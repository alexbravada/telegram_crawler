# tg_crawler

Сервис, который следит за публичными Telegram-каналами через `https://t.me/s/<channel>`,
берёт все посты новее `last_post_id` и публикует их во внешний API (эмулятор, `POST /messages`).

## Документация (читать перед любой задачей)

- `docs/PLAN.md` — план задач T0–T18, правила работы, критерии приёмки. Главный документ.
- `docs/ARCHITECTURE_v2.md` — сервис, API, контракт эмулятора, compose. Приоритет над v1.
- `docs/ARCHITECTURE.md` — v1: парсер, ProxyPool, Feeder/Writer, защита от потерь каналов.

## Ключевые решения (не переспрашивать)

- `title` = название канала; парсятся все посты новее `last_post_id`.
- Посты сохраняются в outbox (`pending_posts`) до публикации, доставка из outbox отдельным циклом.
  SLA: потери постов ≤ 1/1000.
- В `POST /watch_channels` приоритет у `channel_name`; `channel_id` (-100…) необязателен,
  хранится в БД и в контракт НЕ уходит. В контракт поле `channel_id` = `channel_name`.
- `caption` у медиа передаётся, только если задан.
- Удаление мягкое, по одному: `DELETE /watch_channels/{channel_name}`.
- Краулер — отдельный процесс, одна реплика. API и краулер общаются только через PostgreSQL.
- SQLAlchemy 2.0 async + asyncpg, Alembic. Прокси: 0–1 в тесте, от 5 в проде.

## Как работать

- Выполнять задачи из `docs/PLAN.md` строго по порядку, по одной.
- После задачи: `ruff check`, `ruff format --check`, `mypy tg_crawler`, `pytest` — всё зелёное.
- Не запрашивать t.me вне задач T4, T17, T18.
- Неоднозначно — остановиться и спросить.
- В конце задачи отметить её в `docs/PROGRESS.md`: номер, статус, изменённые файлы, расхождения со спекой.
- После каждой задачи делать git-коммит (изменённые доки + код задачи, отдельно от других задач).
